# Migrating from V2bX-managed Elise

V2bX v0.6.8 bundled Elise 1.0.3. Standalone Elise starts at v1.0.4. Versions
passed to the new installer refer to `phungvanquy/elise` releases, not V2bX tags.

## Before migration

Install standalone Elise using the root installer in the README. This installs
tools and a service template without starting or changing legacy instances.
Run `sudo elisectl migrate --from-v2bx --dry-run` to inspect the migration.
Dry run reads configuration and service metadata, changes no files or services,
and does not contact a certificate authority.

Automatic migration supports the per-node services generated by the old V2bX
helper. It preserves enabled/running states independently, the stock root
service identity, and ordinary resource-limit/restart drop-ins. Modified
ExecStart/WorkingDirectory, configuration environment overrides, environment
files, service sandboxes, masked instances, and alternate service users require
manual review before any services are stopped. Existing standalone instance
names are never overwritten.

Certificates or other configured files under `/etc/V2bX` or `/usr/local/V2bX`
must be relocated first, together with their certificate-tool configuration and
renewal hooks: a later V2bX uninstall deletes those directories. Arbitrary
external certificate paths are retained. Credentials are never rewritten by
search-and-replace.

## Migrate

```bash
sudo elisectl migrate --from-v2bx --dry-run
sudo elisectl migrate --from-v2bx
sudo elisectl list
sudo elisectl status hysteria2-102  # substitute your actual instance
sudo elisectl log hysteria2-102
```

Running nodes restart, briefly disconnecting clients. Stopped nodes remain
stopped. Each old service is stopped, disabled, and masked before its new
counterpart starts. The migrator checks panel settings and the TCP/UDP listener
for each running node. Inspect panel reporting and test a client afterward;
these startup checks do not exercise a real client session.

Configuration and certificates are copied to `/etc/elise/instances/<instance>`.
Migrated services receive individual unit files and effective drop-ins under
`/etc/systemd/system/elise@<instance>.service*`, preserving their settings
independently of the template used by newly added nodes.

The final step replaces cached `/usr/bin/V2bX-elise` with a retirement notice.
Its `uninstall` action does nothing, so an old V2bX manager cannot uninstall the
standalone service. Re-running migration skips completed nodes after verifying
that their legacy services remain stopped and masked.

## Preserve traffic state

Keep `/etc/v2bx-elise/<instance>`. The config loader normally stores the IP cache
and `traffic/` pending-report files next to the original configuration; explicit
`ip_user_cache_save_dir` settings can select another location. Migration writes
the effective old directory into the new configuration. Relative state paths
are resolved against the old working directory.

Both executables therefore use the same current pending-report files during
rollback. Never restore `traffic/` from an earlier backup: reports acknowledged
since that snapshot could otherwise be sent twice. State relocation is a
separate maintenance operation.

Update external certificate renewal hooks to `elisectl restart <instance>`.
If your certificate tool writes into the old instance directory, update its
output paths too. Automatic HTTP-01 renewal follows the copied configuration.

## Failure and recovery

The installer and migrator print a private backup directory under
`/var/lib/elise/backups/`. Migration saves original configuration, service files,
helper bytes, and original running/enabled states. `migration.json` records the
outcome; `files.json` maps original file paths to saved bytes and modes.
Installation has an analogous `install.json` record.

On an ordinary failure, migration stops new instances, removes their new files,
restores changed files, unmasks old services, and restores their boot/running
states. It retains current traffic state. If stopping a new service or restoring
an old one fails, it reports `rollback-incomplete` and retains its backup.

A power loss or SIGKILL cannot run automatic rollback. Before manual recovery,
inspect backup JSON records and systemd states. Stop and disable the new instance
before unmasking or starting the old one. Restore old executable/helper files
from the backup if necessary; preserve live traffic files. For an originally
running and enabled node:

```bash
sudo systemctl disable --now elise@hysteria2-102.service
sudo systemctl unmask V2bX-elise@hysteria2-102.service
sudo systemctl enable --now V2bX-elise@hysteria2-102.service
```

Restore originally stopped or disabled nodes to those states instead. Never run
both service names for one panel node. After manual recovery, review/remove its
standalone instance and marker before rerunning migration; existing destinations
cause it to stop for review. Migration retains the old executable and service
template for recovery. Historical V2bX archives remain in the V2bX releases.
