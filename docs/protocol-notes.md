# Protocol and runtime notes

For native configuration, `cert_mode=http` (alias `acme`) enables automatic HTTP-01 issuance; set `cert_domain`, `acme_email`, `cert_file`, and `key_file`. The wizard uses `acme_server=letsencrypt` and `cert_key_length=ec-256`. The responder supports IPv4 and IPv6, waits up to two minutes for another instance to release TCP port 80, and bounds an issuance attempt to four minutes. Every 12 hours, Elise checks the certificate's expiry, hostname, and matching private key. Successful renewal reloads the inbound independently of panel availability; this may disconnect active sessions. Failed renewal retains a still-valid certificate. An unusable certificate at first startup stops the node.

`cert_key_length` supports `ec-256` (default), `ec-384` (`p384` or `p-384`), `rsa-2048` (`2048` or `rsa`), and `rsa-4096` (`4096`). RSA keys use the requested modulus size and are generated in a background worker. The HTTP-01 responder accepts requests split across TCP packets, with an 8 KiB header limit and a 10-second header timeout.

`cert_mode=file` uses supplied files. A self-signed certificate generated by the wizard or `--cert-mode=self-signed` is valid for 3650 days (about 10 years) and also uses file mode, preserving its identity across restarts. These certificates are not renewed automatically; existing certificates retain their original expiry when Elise is updated. `auto_tls` is a separate fallback that generates a self-signed certificate in memory; it is not ACME. The wizard sets `auto_tls=false` in all three modes. DNS-01 is not implemented.

## Hysteria 2

Elise follows V2bX's bandwidth negotiation: a client with a receive rate uses a paced Brutal controller, capped by the panel's `up_mbps`; a client advertising zero uses BBR. Panel directions are from the server's perspective: `up_mbps` is server transmit and `down_mbps` is server receive. Both are converted from Mbps to bytes per second for the [Hysteria 2 protocol](https://v2.hysteria.network/docs/developers/Protocol/). A zero server receive limit is advertised as `0` (unlimited), preserving the client's requested upload rate. `ignore_client_bandwidth` (also `ignoreClientBandwidth`) selects BBR and advertises `auto` instead. Brutal's loss compensation is bounded to 25%; Quinn supplies byte-based loss samples.

Authentication retries preserve the connection's original user and negotiated rate. With domain sniffing enabled for an IP target, Elise sends the TCP acceptance before reading application data, as V2bX's request hook does; a later audit or dial failure closes the stream. UDP replies support Go clients that omit the datagram transport parameter in their Chrome-style handshake. Obfuscated UDP receives split kernel-coalesced packets before decoding each salt, and listeners request larger kernel send/receive buffers subject to OS limits.

Run the Hysteria unit tests with `cargo test --locked --lib protocol::hysteria`. From this directory, the optional interoperability test builds the Hysteria Go client pinned in `tests/interop/hysteria2` and checks concurrent TCP, sniffed audit rules, fragmented UDP, Salamander, and bandwidth negotiation:

```bash
cargo test --locked --test hysteria2_v2bx -- --ignored --nocapture
```

## Online IP limits

Local IP limits do not require Redis. An authenticated session holds one slot for its normalized client IP; multiple sessions from that IP share the slot. The last session closing releases it immediately, and active sessions stay counted beyond `device_limit_window`. IPv4 uses `/32` and IPv6 uses `/64` by default. Locking a phone's screen does not necessarily close its VPN connection.

On Linux, TCP listeners enable keepalive after 30 seconds of idle time, with three probes 10 seconds apart. This helps detect a device that disappears without closing its connection; it is not an immediate offline signal. UDP/QUIC sessions use their protocol timeouts. Relay traffic, proxies, and transport timeouts can affect disconnect detection.

Online reports explicitly clear disconnected users at the next `submit_interval`, and failed reports are retried. UniProxy alive counts include this instance's own reports: Elise discounts recently acknowledged local counts for the panel's 120-second IP lifetime plus its 60-second totals cache to avoid counting them twice during cached updates. Panel-based cross-node counts remain approximate because they provide totals rather than IP identities.

Shared Redis is optional for cross-instance IP checks. Its existing timestamp-based records expire according to `conn_limit_expiry`; local disconnect cleanup does not delete a shared IP record that another instance may still use. These changes require rebuilding/updating the Elise binary and restarting the instance.

## XHTTP

Elise accepts `packet-up`, `stream-up`, `stream-one`, and `auto` over HTTP/1.1 and HTTP/2, including TLS. Packet uploads share an ordered session across requests and connections within the same inbound. HTTP/3 is not implemented.

For GET uploads carried in headers, use these panel network settings:

```json
{
  "host": "example.com",
  "path": "/api/v1/sync",
  "mode": "packet-up",
  "extra": {
    "uplinkHTTPMethod": "GET",
    "uplinkDataPlacement": "header",
    "uplinkDataKey": "X-Data",
    "scMaxEachPostBytes": 2048,
    "uplinkChunkSize": 2048,
    "xPaddingBytes": "100-1000",
    "xPaddingObfsMode": true,
    "xPaddingPlacement": "queryInHeader",
    "xPaddingHeader": "X-Padding",
    "xPaddingKey": "x_padding",
    "xPaddingMethod": "repeat-x"
  }
}
```

Elise supplies the four padding defaults shown above when they are omitted. Keep them explicit for clients that do not supply these defaults themselves. Both peers must agree on the padding and data settings. A Clash/Mihomo subscription must translate `extra` into the corresponding fields under `xhttp-opts`; copying only `host`, `path`, and `mode` will fail.

Packet payloads can be in the body, numbered base64url headers (`X-Data-0`, `X-Data-1`, ...), or cookies (`x_data_0`, ...). `auto` data placement accepts all three. `scMaxEachPostBytes` limits the decoded payload per request and accepts a positive integer, numeric string, or range; the server uses the upper bound. `uplinkChunkSize` controls client header/cookie splitting, so the server joins chunks independently of that value. GET and explicit header/cookie uploads require `packet-up` mode.

Padding supports `header`, `queryInHeader`, `cookie`, and `query` placement with `repeat-x`. A query-only placement has no corresponding URL in an HTTP response. Other padding methods, including `tokenish`, are rejected at configuration time. Session and sequence metadata support path, header, cookie, and query placement using Xray's `sessionIDPlacement`/`sessionIDKey` (also `sessionPlacement`/`sessionKey`) and `seqPlacement`/`seqKey` options.

`scMaxBufferedPosts` defaults to 30 pending packets per session. Uploads without a download expire after 30 seconds; an inbound admits at most 4096 sessions. `serverMaxHeaderBytes` defaults to 8192. Invalid padding returns HTTP 400, oversized decoded uploads return 413, duplicate packets/downloads return 409, and a full packet queue returns 429. Closing the download releases its session and cancels the protocol handler.

Run the transport tests with `cargo test --lib transport::xhttp`. An optional interoperability test exercises the local Tunnio core over self-signed TLS, with HTTP/1.1, HTTP/2, and concurrent VLESS sessions:

```bash
TUNNIO_CORE_DIR=/path/to/Tunnio/core cargo test --test xhttp_tunnio -- --ignored --nocapture
```
